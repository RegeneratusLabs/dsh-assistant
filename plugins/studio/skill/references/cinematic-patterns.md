# Cinematic Patterns · best practice for a workflow demo

> Five key patterns for upgrading from "PPT animation" to "launch-event-grade cinematic".
> Distilled from the two cinematic demos in the 2026-04 "Let's Talk Skills" deck (the Nuwa workflow + the Darwin workflow); reproducible as tested.

---

## 0 · What this document solves

When you need a "demo animation that demonstrates a workflow" (typical cases: skill workflows, product onboarding, API call flows, agent task execution), there are two common approaches:

| Paradigm | What it looks like | Consequence |
|---|---|---|
| **PPT animation** (bad) | step 1 fade in → step 2 fade in → step 3 fade in, 4 boxes arranged on one screen | the audience reads it as "a PPT with fades added", no wow moment |
| **Cinematic** (good) | scene-based: one thing in focus at a time, dissolve / focus pull / morph between scenes | the audience reads it as "a product launch clip" and wants to screenshot and share it |

The root of the difference is **not animation technique** — it's **narrative paradigm**. This document covers how to upgrade from the former to the latter.

---

## 1 · Five core patterns

### Pattern A · Dashboard + cinematic overlay, a two-layer structure

**Problem**: a plain cinematic defaults to a black screen with a ▶ button. If the user lands on that page and doesn't click, they see nothing at all.

**Solution**:
```
DEFAULT state (always visible): the full static workflow dashboard
  └── the audience sees at a glance how this skill / workflow runs

CLICK ▶ (the overlay floats up): 22-second cinematic
  └── fades back to DEFAULT automatically when it ends

```

**Implementation notes**:
- `.dash` visible by default; `.cinema` defaults to `opacity: 0; pointer-events: none`
- `.play-cta` is a small gold button in the bottom-right corner (not a big center overlay)
- On click → `cinema.classList.add('show')` + `dash.classList.add('hide')`
- Run once with `requestAnimationFrame` (not a loop); call `endCinematic()` to reverse the state when it ends

**Anti-pattern**: default = a big centered ▶ overlay covering everything, with a blank page until someone clicks.

---

### Pattern B · Scene-based, NOT step-based

**Problem**: chopping the animation into "step 1 appears → step 2 appears → ..." is PPT thinking.

**Solution**: split it into 5 scenes; each scene is an **independent shot**, and the full screen focuses on one thing:

| Scene type | Job | Duration |
|---|---|---|
| 1 · Invoke | user input triggers (terminal typewriter) | 3-4s |
| 2 · Process | the core workflow, visualized (a distinct visual language) | 5-6s |
| 3 · Result/Insight | the key artifact distilled out (visualized) | 4-5s |
| 4 · Output | the actual artifact on display (files / diff / numbers) | 3-4s |
| 5 · Hero Reveal | the closing hero moment (big type + value proposition) | 4-5s |

**Total ≈ 22 seconds** — the tested golden length:
- Under 18 seconds: the PM hasn't engaged yet and it's already over
- Over 25 seconds: they lose patience
- 22 seconds is exactly enough for "hook → unfold → gather → leave an impression"

**Implementation notes**:
- `T = { DURATION: 22.0, s1_in: [0, 0.7], s2_in: [3.8, 4.6], ... }` as the global timeline
- A single `requestAnimationFrame(render)` computes opacity / transform for every scene
- No setTimeout chains (they break easily and are hard to debug)
- Easing must be `expoOut` / `easeOut` / cubic-bezier; **linear is forbidden**

---

### Pattern C · Every demo's visual language must be independent

**Problem**: after the first cinematic, you cut corners on the second by reusing the same template (same orbit + pentagon + typewriter + big hero type) and only swapping the copy.

**Consequence**: the audience notices the two skills "look identical", which says "these two skills are no different".

**Solution**: each workflow has a different core metaphor, so the visual language has to differ too.

**Side-by-side case**:

| Dimension | Nuwa (distilling a person) | Darwin (optimizing a skill) |
|---|---|---|
| Core metaphor | collect → distill → write | loop → evaluate → ratchet |
| Visual motion | floating / radiating / pentagon | looping / rising / comparing |
| Scene 2 | 3D Orbit · 8 archive cards floating on a perspective ellipse | Spin Loop · tokens running 5 laps around a 6-node ring |
| Scene 3 | Pentagon · 5 tokens radiating from the center | v1 vs v5 · side-by-side diff (red version vs gold version) |
| Scene 4 | SKILL.md typewriter | Hill-Climb · full-screen curve drawing |
| Scene 5 hero | "21 minutes" in big serif italic | spinning gear ⚙ + a gold "KEPT +1.1" tag |

**Test**: cover the copy and look at the visuals alone — can you tell which demo this is? If you can't, it's laziness.

---

### Pattern D · Use real material generated by AI, not emoji or hand-drawn SVG

**Problem**: a 3D orbit / gallery needs material fragments floating in it; emoji (📚🎤) are ugly and carry no brand, and hand-drawn SVG book spines never look like real books.

**Solution**: run one 4×2 grid sheet through `huashu-gpt-image` (8 theme-related objects · white background · 60px breathing space · unified style), then cut it into 8 separate transparent PNGs with `extract_grid.py --mode bbox` from the `huashu-gpt-image` repository.

**Prompt essentials** (detailed prompt patterns are in the `huashu-gpt-image` skill):
- IP anchoring ("1960s Caltech archive aesthetic" / "Hearthstone-style consistent treatment")
- White background (easy to cut out; a gray background sets a nicer mood but makes transparent extraction hard)
- 4×2 rather than 5×5 (avoids the last-row compression bug)
- Persona finishing ("You are a Wired magazine curator preparing an exhibition photo")

**Anti-pattern**: emoji as icons, CSS silhouettes in place of product shots.

---

### Pattern E · BGM + SFX two-track system

**Problem**: animation with no sound and the audience subconsciously reads it as "a cheap demo".

**Solution**: a long BGM bed + 11 SFX cues.

**Generic SFX cue recipe** (works for workflow demos):

| Time | SFX | Trigger |
|---|---|---|
| 0.10s | whoosh | the terminal rises from below |
| 3.0s | enter | the typewriter finishes, enter is pressed |
| 4.0s | slide-in | scene 2 elements enter |
| 5-9s × 5 | sparkle | key process nodes (each generation / each token / each data point) |
| 14s | click | switch to the output scene |
| 17.8s | logo-reveal | the hero reveal moment |
| typewriter | type | fire once per 2 characters (don't overdo the density) |

**Frequency separation**: BGM volume 0.32 (low-frequency bed), SFX volume 0.55 (mid-high punch), sparkle 0.7 (has to stand out), logo-reveal 0.85 (the strongest hero moment).

**User control**:
- A ▶ start overlay is mandatory (browser autoplay restrictions)
- A small mute button in the top-right (the user can silence it at any time)
- Never "it blares the moment you land on the page"

## 2 · Static dashboard design notes

The dashboard is Layer 1 of the two-layer structure; the PM can understand the skill without pressing ▶.

**Layout**: a 3-column grid (or 1 large + 2 small); each panel answers one question:

| Panel type | What it answers | Example |
|---|---|---|
| **Pipeline / Flow Diagram** | "What is this skill's workflow?" | Nuwa 4-stage pipeline · Darwin autoresearch loop |
| **Snapshot / State** | "What does the real data look like?" | Darwin 8-dimension rubric snapshot |
| **Trajectory / Evolution** | "How does it change across runs?" | Darwin 5-generation hill-climb curve |
| **Examples / Gallery** | "What has it produced already?" | Nuwa 21-persona gallery |
| **Strip · Example I/O** | "What goes in → what comes out" | Nuwa example strip: `› nuwa distill Feynman → feynman.skill (21 min)` |

**Key constraints**:
- Information density has to be high enough (every panel must carry differentiated information)
- But no data slop (every number has to mean something)
- Colors must match the cinematic (same family, so the switch isn't jarring)

## 3 · Debugging and development tools

Any long animation needs three dev tools, or debugging explodes.

### Tool 1 · `?seek=N` freezes at second N

```js
const seek = parseFloat(params.get('seek'));
if (!isNaN(seek)) {
  started = true; muted = true;
  frozenT = seek;  // render() uses this t instead of elapsed
  cinema.classList.add('show'); dash.classList.add('hide');
}

// inside render():
let t = frozenT !== null ? frozenT : (elapsed % T.DURATION);
```

Usage: `http://.../slide.html?seek=12` shows the frame at second 12 directly, no waiting for playback.

### Tool 2 · `?autoplay=1` skips the ▶ overlay

Handy for automated playwright screenshot tests, and for force-starting playback when embedded in an iframe.

### Tool 3 · A manual REPLAY button

A small button in the top-right; the user or a debugger can replay as many times as needed. CSS:

```css
.replay{position:absolute;top:18px;right:18px;background:rgba(212,165,116,0.1);
  border:1px solid rgba(212,165,116,0.3);color:#D4A574;
  font-family:monospace;font-size:10px;letter-spacing:.28em;text-transform:uppercase;
  padding:6px 12px;border-radius:1px;cursor:pointer;backdrop-filter:blur(6px);z-index:6}
```

## 4 · iframe embedding traps (when the cinematic is embedded in a deck)

### Trap 1 · the parent window's click zones swallow the buttons inside the iframe

If the deck's index.html adds "transparent 22vw click zones on the left and right to turn pages", they **cover the ▶ play button inside the iframe** — the user's click on the button is swallowed as "next page".

**Fix**: give the click zones `top: 12vh; bottom: 25vh`, leaving the top and bottom 25% unintercepted so both the center ▶ and the bottom-right ▶ inside the iframe stay clickable.

### Trap 2 · the iframe takes focus and keyboard events are lost

After the user clicks the iframe, focus lives inside it and the parent window stops receiving ←/→ key events.

**Fix**:
```js
iframe.addEventListener('load', () => {
  // inject a keyboard forwarder
  const doc = iframe.contentDocument;
  doc.addEventListener('keydown', (e) => {
    window.dispatchEvent(new KeyboardEvent('keydown', { key: e.key, ... }));
  });
  // pull focus back to the parent window after a click
  doc.addEventListener('click', () => setTimeout(() => window.focus(), 0));
});
```

### Trap 3 · file:// vs https:// behave differently

A cinematic that tests fine on local file:// can break once deployed, because:
- under file:// the iframe contentDocument is same-origin
- under https:// it's also same-origin (same host), but audio autoplay restrictions are stricter

**Fix**:
- Before deploying, test once over local HTTP with `python3 -m http.server`
- BGM must only call `bgm.play()` after the user clicks ▶; never play on page load

## 5 · Anti-pattern quick reference

| ❌ Anti-pattern | ✅ Pattern |
|---|---|
| default = black screen with a ▶ overlay | default = static dashboard; ▶ is secondary |
| 4 steps side by side, fading in on one screen | 5 scenes switching full-screen, one focus per scene |
| reuse a template with new copy for a different demo | independent visual language per demo (distinguishable with the copy covered) |
| emoji / hand-drawn SVG as material | gpt-image-2 sheet + extract_grid cutout |
| no BGM, no SFX | BGM + 11 SFX cues, two tracks |
| setTimeout chains for scheduling | requestAnimationFrame + a global timeline T object |
| linear animation | Expo / cubic-bezier easing |
| no dev tools | `?seek=N` + `?autoplay=1` + REPLAY button |
| iframe buttons swallowed by the parent's click zones | give the click zones top/bottom margins to make room for the buttons |

## 6 · Time budget

Following this pattern, one complete cinematic demo (dashboard included):

| Task | Time |
|---|---|
| Design the 5-scene narrative + visual language | 30 minutes (be careful — this decides independence) |
| Dashboard static layout + content | 1 hour |
| Implement the 5 cinematic scenes | 1.5 hours |
| Tune audio cue timing + replay button | 30 minutes |
| Verify 5 key moments with Playwright screenshots | 15 minutes |
| **Total per demo** | **3-4 hours** |

The second demo reuses the framework, but **the visual language must be independent**; about 2-3 hours.
