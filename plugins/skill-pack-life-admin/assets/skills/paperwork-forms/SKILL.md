# Paperwork forms

A form is a fixed set of questions, so the work is a fixed set of steps: read all of it, translate every
question, ask everything once, and fill in only what the user actually said. Blanks stay marked, decisions
are handed back, and nothing is signed, paid or submitted.

## When to use

- "Help me fill in this form." / "Fill in this application with me."
- "This application is confusing" — a benefits claim, a permit, a licence, a school or childcare form, a housing or rental application, a grant, a registration.
- "What does question 7 mean?" / "what are they actually asking for here?"
- "Where do I start?" on a long form — forty questions and no obvious first move.
- "What do I need to attach?" / "do they want originals or copies?"
- A renewal or re-application form that has to match what they sent last time.
- They have the form and the supporting documents, and want the whole thing prepared before they sit down to it.

## When not to use

- **Explaining a letter or notice they received** — go to `explain-this-document`.
- **A contract or set of terms they have to agree to** rather than fill in — that is reading, not answering. Go to `explain-this-document`.
- **Free-form writing that goes with an application** — a personal statement, a cover letter, a motivation section. That is writing, not a form.
- **Submitting the form for them** — logging into a portal, clicking submit, paying a fee. This skill produces answers; the user enters and submits them.
- **Deciding eligibility or entitlement** — "am I allowed to claim this", "should I tick yes to that". The authority decides; the skill explains what the question asks and marks it for the user.
- **Calculating a tax position** — a return with income or deductions that need judgement belongs with an accountant.

## Procedure

1. **Read the whole form before answering anything.** Count the questions, note the sections, the page numbers, and the instructions — including page one and the last page, which people skip. The last page usually holds the declaration the user must sign.

   **Done when:** you can say how many questions there are, in which sections, and quote every instruction about deadlines, fees, signatures and supporting documents.

2. **Translate every question into plain language.** Keep the form's own numbering and wording next to the plain version, so the user can find each one on paper. Mark any question that is ambiguous, duplicated elsewhere, or that assumes something the user may not have.

   **Done when:** the number of translated questions equals the number of questions on the form, and each entry shows both the original wording and the plain version.

3. **Work out what the form is really collecting.** Many forms ask for the same fact twice in different words. Note which answers feed several questions, which questions are optional, and which are conditional — "only if you answered yes to question 4".

   **Done when:** every question is marked required, optional, or conditional with the condition stated, and any answer used more than once is named.

4. **Interview the user once, in one batch.** Group the questions by theme, ask only what the form needs, number the items to match the form, and end with "skip anything you can't answer yet — I'll mark it". One message, never one question at a time. If the user has given documents, ask them for the facts the documents already contain rather than from memory.

   **Done when:** every needed question was asked in a single message, and each is either answered or listed as outstanding on the user's instruction.

5. **Fill in only what the user supplied.** Three states per answer and nothing else: the user's own answer; `TO CONFIRM` when a fact is missing; `YOUR DECISION` when the choice belongs to the user, with the trade-off in one line. Never invent a date, a number, an address, a reference, or an eligibility claim — a wrong answer on an official form is worse than a blank one.

   **Done when:** every answer is either the user's words, `TO CONFIRM`, or `YOUR DECISION` with a note, and none is a guess.

6. **Check the facts against the documents.** Wherever the user gave a figure, a date or a reference that also appears on a document they hold, have them read it off the document rather than from memory, and correct the draft.

   **Done when:** every figure, date and reference that exists on a document has been confirmed against that document or downgraded to `TO CONFIRM`.

7. **List the required attachments.** Each item comes from a specific instruction or question, with the format the form asks for where it says so (copy, certified copy, original, photo, translation) and any deadline.

   **Done when:** each attachment cites the page or question that requires it, and the list states the format whenever the form states one.

8. **Assemble the submission pack.** Answer table (question number | form wording | plain wording | the answer to write), attachment checklist, and a "before you send" list: sign, date, keep a copy, fee if any, where it goes, and how long a decision usually takes if the form says.

   **Done when:** the table covers every question, the checklist covers every attachment, and the before-you-send list names the submission route the form itself states.

9. **Hand over with the blockers first.** State how many answers are ready, how many are outstanding, and the single thing that stops submission today. Nothing is signed, submitted or paid.

   **Done when:** the chat reply gives the ready/outstanding counts, the blocking item, and says plainly that nothing was submitted.

## Gotchas

- Read to the end. The declaration on the last page and the attachment list are the two things people miss, and both cause rejections.
- Dates have a required format. Match the form's own example — a rejected format is a rejected form.
- "Optional" is not always optional in practice. If the guidance implies an answer is expected, say so and let the user decide.
- Don't scatter "N/A" everywhere. Some systems reject it, some treat it as a false statement. Ask what the form's guidance says, or leave it `TO CONFIRM`.
- Never sign, submit, or pay on the user's behalf, and never enter anything into a portal.
- Eligibility questions belong to the authority. Give the user the wording to read and the question to ask, not a verdict.
- Answers can contradict each other — two addresses, overlapping dates, an income that doesn't add up. Surface the conflict and ask which is right; don't silently pick one.
- The user should keep a copy of exactly what they submitted, including the date.
- If the form is in a language the user doesn't read, say the translation is your own and not certified, and check whether a certified translation is required.
- If part of the form is missing or illegible, say which questions you could not cover rather than filling the gap with a reasonable-looking answer.

## Output

- **`form-answers.md`** — the answer table (question number | form wording | plain wording | answer to write), the attachment checklist, and the before-you-send list. If the user supplied the form as an editable file and asks for it, the same answers can go into a filled copy of that file, with the table kept as the record.
- **In chat:** how many questions are answered and how many are outstanding, the attachments to gather, the one thing blocking submission, and a plain statement that nothing was submitted.
